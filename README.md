# JobIndex

A job board indexer: pulls postings from ATS platforms (Greenhouse, Lever, Workday, …) and
job-board platforms into one searchable, continuously updated PostgreSQL index.

Project rules (stack, connector conventions, crawling etiquette) are in [CLAUDE.md](CLAUDE.md).

## Quick start

Requirements: Docker with Compose v2.24+ and `make`. Everything runs in containers
(Python 3.12), so no local Python setup is needed.

```sh
make up        # build + start postgres and the app: search page http://localhost:8000/, API docs /docs
make migrate   # apply database migrations
make test      # offline test suite (fixtures, jobindex_test database)
make test-live # live tests against real employer boards (network)
make lint      # ruff + mypy
make coverage  # live-crawl done platforms' examples, regenerate docs/COVERAGE.md
make seed-demo # register the example boards of every done platform (real data)
make seed-demo FILE=coverage/demo_sources.yaml  # only the small boards of the hosted demo
make crawl     # crawl every active source (then dedup)
make db-size   # database + table sizes; make prune: drop old closed postings/history
make fill-rates # field fill rates per platform (ARGS=--markdown)
```

Challenge audit with evidence for every criterion: [docs/CHALLENGE_CHECKLIST.md](docs/CHALLENGE_CHECKLIST.md).

Platform coverage and the work plan for the remaining platforms live in
[docs/COVERAGE.md](docs/COVERAGE.md), generated from `coverage/platforms.yaml`.

Register and crawl a board:

```sh
docker compose run --rm app python -m jobindex.cli add-source https://jobs.lever.co/spotify
docker compose run --rm app python -m jobindex.cli add-source https://www.figma.com/careers/
docker compose run --rm app python -m jobindex.cli crawl 1      # or: make crawl SOURCE=1
make crawl                                                     # all active sources
docker compose run --rm app python -m jobindex.cli schedule    # crawl continuously
```

Then search at http://localhost:8000/ or via the API (`GET /jobs?q=python&location=Berlin`,
`GET /stats`; OpenAPI docs at `/docs`). Results are deduplicated: an opening listed on
several sources is returned once, with every source's link.

`add-source` accepts hosted board URLs, job URLs, embed URLs, API URLs, and custom-domain
careers pages. For the last kind it downloads the page (respecting robots.txt) and looks for
platform fingerprints (embed scripts, iframes, links to the hosted board).

Platforms without a usable API use the **generic sitemap + JSON-LD connector**
(`jobindex/connectors/generic_jsonld.py`): job URLs from the board's sitemap, one request
per *new or changed* job page (sitemap `<lastmod>`), schema.org `JobPosting` from the page.
Each platform is a thin subclass (sitemap location, job-URL pattern, page fingerprint for
custom domains):

| HiringThing | `{company}.hiringthing.com/api/rss.xml` (RSS) | host; global S3 sitemap not addressable per tenant |

| iCIMS | `{host}/sitemap.xml` | host (`careers-x.icims.com` or custom domain) |
| Jobboardly, JBoard, Niceboard, SmartJobBoard | `{board}/sitemap.xml` (index) | host; JBoard has no `<lastmod>` |

| SuccessFactors (RMK sites) | `{site}/sitemap.xml` | host; Java-style dates |

Generic-connector safety: a posting whose `validThrough` passed, or whose page says it is
closed/expired (or answers 404/410), is stored **closed** and not re-fetched until its
`<lastmod>` changes; a crawl that finds more than `GENERIC_MAX_JOB_DROP` (default 50%)
fewer open postings than the last successful one fails instead of closing them; fetched
pages are checkpointed every 100, so a failed first crawl of a big board resumes.

Sites that refuse us (robots.txt rule or HTTP 403) are listed with request-level evidence in
`coverage/blocked_by_site.yaml`.

## How a crawl works

1. A `fetch_runs` row is created (`running`).
2. The source's connector returns the complete list of open postings — or raises.
   Platforms without descriptions in their list endpoint (Workday, Oracle, BambooHR,
   Rippling, SmartRecruiters, all generic sitemap connectors) get one detail request per
   *new or changed* posting (`detail_cache_key`; for sitemap platforms the `<lastmod>`,
   stored in `jobs.list_version`); unchanged postings reuse stored details (progress is
   logged every 100 jobs). Long fetches (Workday lists, generic job pages) save progress
   in `sources.crawl_checkpoint`; if the crawl fails half-way, the next attempt resumes
   there (Workday: max 2 h old; generic pages: max 24 h).
   Postings are then normalised (`RawJob.normalized()`).
3. **Failure**: the run is marked `failed`, `sources.consecutive_failures` is incremented,
   and no job is modified. A failed fetch is never interpreted as "all jobs closed".
4. **Success**: new postings are inserted; postings whose `content_hash` changed are updated
   with one `job_changes` row per changed meaningful field (`normalize.HASH_FIELDS`);
   cosmetic changes (URLs, HTML markup, dates) are applied silently; postings that
   disappeared are closed; closed postings that reappear are reopened; postings whose
   `expires_at` has passed are stored/kept closed. Connectors can opt into a job-count
   drop guard (`max_job_drop()`): a result with too few open postings fails the run.
5. **Dedup** (`jobindex/dedup/`) then regroups postings of the same opening across sources
   (`jobs.canonical_job_id`); see [docs/CONNECTORS.md](docs/CONNECTORS.md#deduplication).

Full-text search uses a generated, weighted `tsvector` column (title > company >
description) with a GIN index, queried via `websearch_to_tsquery`.

## Adding a connector

Full guide: [docs/CONNECTORS.md](docs/CONNECTORS.md#adding-a-connector). In short:

1. Create `jobindex/connectors/<platform>.py` with a `@register`-decorated `BaseConnector`
   subclass implementing `detect`, `board_url` and `fetch_jobs` (plus `fetch_job_detail`
   if the list lacks descriptions). Use `self.http` for every request. Check the API
   host's robots.txt first.
2. Save a real response into `tests/fixtures/<platform>/` with
   `docker compose run --rm app python scripts/capture_fixture.py URL tests/fixtures/<platform>/<name>`
   (goes through the polite client), trim it, and note URL + date in the test docstring.
3. Add `tests/connectors/test_<platform>.py`: URL-detection table, fixture test via
   `tests.fakes.mock_http`, and a `@pytest.mark.live` test against 2 real employers.
   `tests/connectors/test_gem.py` (one request) and `test_bamboohr.py` (list + detail) are
   good templates.
4. Mark the platform `done` in `coverage/platforms.yaml` (connector module + 2 examples)
   and run `make coverage`.
